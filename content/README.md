# Adding a weekly brief

This folder holds the **source** for each brief on the site. The build step turns each file into a full HTML page, updates the homepage, RSS feed, and sitemap.

## What belongs here

Add one markdown file per brief:

| Rule | Example |
|------|---------|
| File name | `brief-3.md`, `brief-4.md`, … |
| Location | This folder: `content/` |
| Number | Internal only: sets the address (`/brief/4/`, etc.) and never appears in labels |

Each file has **YAML front matter** at the top (between `---` lines), then the **body** (markdown or HTML).

### Naming and labels (adopted Nov. 18, 2026; replaces the Nov. 7 numbering labels)

- **Labels are short and say when, not what.** The small label above each headline (`eyebrow`) is the timing only, two to five words. The meeting date keeps each label distinct; the headline names the topics. Never use a generic label such as "Council Preview."
  - Before a meeting: `Before the Nov. 17 vote`
  - After a meeting: `Decided Sept. 15–Oct. 6`
  - Tracker reports: `Promised vs. Actual`
  - Off-schedule extras: `Update · Nov. 20`
- **The publish date goes in the byline** (`meta_line`), e.g. `By J Gonzales · Nov. 15, 2026`, plus any `Corrected` or `Updated` dates. Homepage cards (`coverage_label`) show the label plus the short date: `Before the Nov. 17 vote · Nov 15, 2026`.
- **Buttons and links read "Read the brief"** or name the topic. Readers never see brief numbers.
- **Numbers stay internal.** Numbers follow publish order and are assigned only when a piece goes live. Drafts never hold one, published pieces are never renumbered, and file number = address: `content/brief-4.md` is `/brief/4/`. Never change an existing `/brief/N/` address.
- **Substack subject:** `[Label]: headline`, for example `Before the Nov. 17 vote: San José wastewater bid comes in 15% over estimate`. X posts lead with the headline and link to the website page.
- **Label changes are logged** on the Corrections page with the original wording.

### Required front matter

- **title** — Headline on the brief page  
- **description** — Used for search engines and link previews  
- **date** — Publication date as `YYYY-MM-DD` (entered once; the build puts it in the byline and homepage label)

Enter each value once. The build derives the rest:

| Derived | From |
|---------|------|
| Brief number / URL (`/brief/N/`) | Filename `brief-N.md` (internal only; readers never see the number) |
| Series / timing label above the headline | **eyebrow**, or **series** if eyebrow is omitted |
| Byline publish date | **date** |
| Byline “Updated …” date | **date_modified** (when set) |
| Homepage coverage label | eyebrow/series · publish date |

### Common optional fields

- **dek** — Short subtitle under the headline  
- **series** — e.g. `Weekly brief` or `Promised vs. Actual` (also the fallback timing label)  
- **homepage_blurb** — One line on the homepage archive  
- **coverage_label** — Override the generated homepage label (`[eyebrow/series] · [date]`)  
- **eyebrow** — Timing label above the headline (if omitted, the build uses **series**)  
- **date_modified** — When the brief was last corrected or updated (`YYYY-MM-DD`); adds `Updated …` to the byline when **meta_line** is omitted  
- **meta_line** — Override the generated byline. Use only when the byline needs wording the build cannot derive (for example both a Corrected date and an Updated date). Prefer **date** + **date_modified** for new briefs.  
- **body_format** — `markdown` (default) or `html` if you paste full HTML sections  

### Example (new weekly brief in markdown)

```markdown
---
title: Your headline here
description: Plain-English summary for Google, Substack previews, and social links.
date: 2026-10-22
series: Weekly brief
homepage_blurb: One sentence for the homepage listing.
eyebrow: Before the [meeting date] vote
dek: Optional subtitle under the headline.
---

**How to weigh in:** [Day, date, time] Council meeting, City Hall, or by Zoom or phone. Items [6.1, 8.1]. Emailed comments to city.clerk@sanjoseca.gov by [deadline], item number in the subject line, or eComments on the [Legistar calendar](https://sanjose.legistar.com/Calendar.aspx). (Agenda p. [N].)

## What matters this week

- **Deciding:** What the Council is voting on, with a [Legistar source](https://sanjose.legistar.com/Calendar.aspx).
- **Cost:** The dollar figure, as the City states it.
- **For residents:** What changes for people in San José.

## [One section per money item, headline style]

Paragraph text and links here.

## Also on the agenda

- One line per item, with its Legistar link.

## Since our last brief

What happened to the items we previewed, from the minutes (say if they are draft).

- **[Item]:** Passed 9-2. Yes: [members]. No: [members]. Absent: [members]. ([Minutes](https://sanjose.legistar.com/Calendar.aspx), p. [N].)

## On the tracker

One sentence on any change to [Promised vs. Actual](../../tracker/) this week, or "No changes this week."

## Coming up

- [Date]: Two or three money items already on future Legistar agendas, with links.

## J Gonzales's take

Clearly marked opinion, separate from the facts above.

## What happens next

Upcoming votes or deadlines for this week's items.
```

Omit `meta_line` and `coverage_label` unless you need an override. With the example above, the build writes the byline `By J Gonzales · Oct. 22, 2026` and the homepage label `Before the [meeting date] vote · Oct 22, 2026`. If you later set `date_modified: 2026-10-25`, the byline becomes `By J Gonzales · Oct. 22, 2026 · Updated Oct. 25, 2026`.

### Weekly brief sections (adopted Nov. 19, 2026)

- **How to weigh in** goes at the top, as the first paragraph before any `##` heading (the build styles it as a callout): meeting date and time, item numbers, comment deadline and how to comment. Readers should be able to act without scrolling.
- **Since our last brief** lists how each councilmember voted on the items we previewed, taken from the minutes. Say whether the minutes are draft or approved. If the minutes aren't posted, say so; don't infer votes from news reports.
- **On the tracker** is one sentence, linked to the tracker. Leave it as "No changes this week" rather than dropping it.
- **Coming up** is two or three money items already posted on future Legistar agendas, no more.
- **Length:** the article body stays near 1,000 words. New sections replace length; they don't add to it. Keep "Also on the agenda" to one line per item.
- **Weeks with no Council meeting:** the brief still runs. Lead with the most useful City money news that week from official records (committee and commission actions, City audits, budget reports, staff memos to Council), label it with the next decision the lead story points to (for example `Before the Dec. 8 vote`), or `Update · [date]` if there is none, and keep How to weigh in pointed at the next comment opportunity, whether a committee or commission meeting or the next Council date.

Existing briefs `brief-1.md` and `brief-2.md` are good references (Brief #2 uses `body_format: html` for legacy layout).

## Two easy ways to add or edit a brief

### A) Save a file in Windows File Explorer

1. Open this repo on your computer (e.g. `Documents\GitHub\thesanjosesource\content`).
2. Create or edit `brief-N.md` in a text editor (Notepad, VS Code, Cursor, etc.).
3. Save the file.
4. Commit and push to `main` when you are ready to publish (GitHub Desktop, Cursor, or command line).

### B) Create or edit on GitHub in the browser

1. Go to [the content folder on GitHub](https://github.com/knightingale408/thesanjosesource/tree/main/content).
2. Click **Add file** → **Create new file** (or open an existing `brief-N.md` and click the pencil to edit).
3. Name the file `brief-N.md`, paste your front matter and body, and commit to `main`.

## Verify links before you publish

From the **repo root**, run:

```bash
python check_links.py content/brief-N.md
```

Replace `N` with your brief number. The script lists every URL in that file, warns about broken San José Legistar links that omit a **GUID**, and checks HTTP status (404s and other errors).

You can also check the built page:

```bash
python build.py
python check_links.py brief/N/index.html
```

## How publishing works

1. You push changes to the **`main`** branch on GitHub.
2. The **Publish site** workflow runs automatically. It executes `python build.py`, which:
   - Builds `brief/N/index.html` from each `content/brief-N.md`
   - Updates `index.html` (latest brief + archive)
   - Regenerates `feed.xml` and `sitemap.xml`
3. The workflow then deploys **all** site files to the live host ([thesanjosesource.com](https://thesanjosesource.com)).

This repo uses a **production approval** step in GitHub Actions: the deploy waits for an explicit approval before the site goes live. Nothing is partial—every publish is the full site from `main`.

For local preview only, run `python build.py` on your machine; you do not need to publish to see the generated HTML in the repo folder.

## Record pages

City Council meeting and file-number pages are not briefs. Their source is `content/meetings/<YYYY-MM-DD>.md` and `content/items/<file>.md` (for example `26-1183.md`). `python3 scripts/pull_legistar.py` writes them. `python3 build.py` renders `/meetings/` and `/items/`. Rules: `docs/RECORD-SITE.md`.
